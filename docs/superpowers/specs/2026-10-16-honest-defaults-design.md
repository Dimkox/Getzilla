# Getzilla — ТЗ «Честные дефолты»: риск по факту изменения, лёгкий путь для мелочей, защита от платных циклов — design
Дата: 2026-10-16. База: `main` (`ae42fad`, включает PR #87 с `code_graph` и `project_ingestion`, которые используют пакеты H и L).

Этот документ не разрешает push, публикацию, изменение настроек GitHub и удаление веток. Это отдельные решения владельца.

---

## 1.1. Источник и метод

Источник — диалог с Grok о Getzilla (критика лендинга и процесса). Каждый тезис проверен на коде (`.getzilla/getzilla/router.py`, `.grok/hooks/*`, `.getzilla/config/policy.json`, `scripts/install_into.py`, `side-projects/getzilla-landing/index.html`). Классификацию проверял реальный роутер на тестовых формулировках в одноразовом проекте (`/tmp/route_probe.py`, запуск `python3 -I /tmp/route_probe.py <repo>`). В ТЗ попадает только то, что подтвердилось.

## 1.2. Что отброшено

| Тезис Grok | Почему отброшен |
|---|---|
| Ноль звёзд как аргумент о качестве | Это маркетинг, к поведению системы не относится. |
| Бесплатные альтернативы (Cursor, Qwen, Aider, чаты) | Сравнение цен на модели. Работу Getzilla не меняет; чаты без доступа к репозиторию — не альтернатива. |
| «По умолчанию ревью не обязательно» | **Неверно.** Даже «исправь опечатку в README» требует `verification`, `code_review` и `test_review`. Проблема обратная (см. 1.3, факт 2). |
| «Агент может поправить GitHub Actions» | **Неверно.** `.github/**` в `protected_paths`; запись идёт через grant и `getzilla_protected_write.py`. |
| «Getzilla обвешивает проект инфраструктурой» как повод отказаться | Смысл есть, но только как требование к объёму установки (пакет F), а не как довод против продукта. |

## 1.3. Рациональное зерно (подтверждённые факты)

| # | Факт | Доказательство |
|---|---|---|
| 1 | Риск определяется только по ключевым словам промпта, и очевидные рискованные задачи получают `low`. | Роутер: «add a checkout with saved cards» → `low/standard`; «fix login for existing accounts» → `low/micro`; «перепиши обработку оплаты заказа» → `low`; «сделай вход через Google» → `low`; «списывай деньги с карты каждый месяц» → `low`. В `HIGH_RISK` есть «платеж», «payment», «auth», но нет «оплат», «login/логин/вход», «card/карт», «checkout», «subscription/подписк», «списан». |
| 2 | Лёгкого пути нет: мелочь проходит тот же ритуал, что и фича. | «исправь опечатку в README» → `micro`, но `review_agents=[code_reviewer, test_reviewer]` и `required_evidence=[verification, code_review, test_review]`; к тому же `README.md` защищён и требует grant. Лендинг при этом обещает: *«A typo gets a light touch. Payments and logins get the full treatment.»* Фактическое поведение противоположно обещанию. |
| 3 | Платные и неограниченные циклы не распознаются (кейс −$1200). | «сделай в n8n сценарий: генерируй 20 вариантов видео через Kling…», «подключи OpenRouter и гоняй генерацию, пока не получится хорошо» → `low`, `human_gates=[]`. В `policy.json` и `routing.json` нет ни бюджета, ни лимита вызовов, ни стоп-условия. |
| 4 | Принуждение мягче, чем звучит. | `stop_gate.py`: *«soft (warn only, never block stop)»*. `pre_tool_use.py`: *«soft policy gate (fail-open)»*: если хук сломан, действие проходит молча. Жёстко на `main` защищают только required checks и branch protection на GitHub, а их установка не включает и не проверяет. |
| 5 | Агент может написать «тесты прошли», не запуская `getzilla_verify`. | Stop-гейт только предупреждает. Привязка к точному коммиту появляется лишь при запуске verify или CI. |
| 6 | Установка тяжёлая, и основной вес — дубли. | `install_into.build_payload`: **672 файла, 5,8 МБ**. `factory/` — 184 файла. 16 скиллов лежат в **пяти** копиях (80 `SKILL.md`: `.agents`, `.claude`, `.gemini`, `.grok`, `.qwen`), описания агентов — в шести (по 21 файлу в `.claude`, `.codex`, `.gemini`, `.github`, `.qwen`, плюс 42 в `.grok`). Копии ставятся для всех агентов, даже если в проекте используется один. |
| 7 | Обещания лендинга не привязаны к механизмам. | «Hidden tests the agent cannot edit», «final check on a separate server» требуют Trust CI; «only changes that passed every step reach main» требует branch protection. Лендинг этих условий не называет. |
| 8 | Нет измерения выгоды. | Нечем ответить на вопрос «быстрее и надёжнее ли с Getzilla, чем без него»: не считаются ни время и токены ритуала, ни пойманные им дефекты. |
| 9 | Superpowers, BMAD и Spec Kit агентам фактически не доставляются. | `toolchain.json`: *«verified_against; advisory parser, never an install target»*. `install.sh` только спрашивает *«Update third-party tools … [y/N]»*, по умолчанию «нет», а без терминала не делает ничего. При согласии `updater.update_sources` клонирует **`HEAD`** (не закреплённые 6.4.2, 6.12.1, 1.1.0) в `~/.getzilla/vendor`, и **ни один модуль Getzilla эту папку не использует**: скиллы и команды до агента не доходят. |
| 10 | Базы безопасности при сбое тихо пропадают. | Установщик всегда запускает `getzilla_update.py --only osv --only opengrep`, но при сбое печатает только `WARNING` и считает установку успешной. Дальше `verify` даёт `opengrep: skip` (*«opengrep not available»*, *«no OpenGrep rules installed»*) вместо провала. |
| 11 | Стеки кроме Python и PHP распознаются, но не проверяются, и verify молчит. | `repo.py` распознаёт `Cargo.toml` (rust), `go.mod` (go), `.cs` (csharp). В `verification.py` есть проверки только для Python (unittest/pytest, ruff, bandit, coverage), PHP (phpunit, phpstan, phpcs, deptrac), `npm run …` (и `skip`, если нет npm) и общие сканеры (semgrep, trivy, opengrep). Сборки, тестов, линтеров и форматтеров для .NET, Rust, Go, Java и PowerShell нет; отметки «стек не проверен» тоже нет. В `known_vulns.ECOSYSTEMS` нет **NuGet** и Maven. В `toolchain.json` нет .NET SDK, rustup/cargo, Go, JDK. |

## 1.4. Цель

Поведение по умолчанию совпадает с обещанием:
- мелочь, у которой это доказано диффом, проходит быстро;
- платежи, логин и деньги получают полный путь, даже если промпт об этом не говорит;
- платный или неограниченный цикл не уходит в работу без лимита и стоп-условия;
- система честно сообщает, что она принуждает, а что только советует.

## 1.5. Решения

1. **Риск = max(промпт, дифф).** Классификация по промпту остаётся (даёт ранние подсказки). На verify считается **риск диффа** по точному HEAD: пути, символы, привязки к архитектуре, зависимости, CI. Риск может только повышаться. При повышении маршрут дополняется требованиями, и verify в режиме `pr` не проходит, пока они не выполнены. Источники: `code_graph` (impact и `architecture_bindings`), правила путей из `routing.json`.
2. **Профили проверки по доказанному диффу.**
   - `trivial` — изменены только тексты, без кода, тестов, конфигов и CI; доказано классификатором диффа. Требуется verification и **один** независимый ревьюер.
   - `standard` — как сейчас.
   - `full` — high-risk.
   Инвариант «автор не одобряет свою работу» сохраняется на всех профилях.
3. **Cost guard.** Признаки платной или неограниченной операции ищутся в промпте и в диффе: известные платные SDK и хосты, n8n-сценарии с циклами, `while True` или retry без максимума вокруг сетевого вызова. Если найдены, в change record должен быть бюджетный контракт (`max_calls`, `max_spend_usd`, `stop_condition`, `alert`) и тест, доказывающий ограничение, а первый живой запуск закрыт human gate. В тестах живых платных вызовов нет.
4. **Честный уровень принуждения.** `getzilla doctor --enforcement` показывает фактический уровень: `advisory` (только хуки), `ci-enforced` (required checks на точный head), `external` (Trust CI). Сбой fail-open-хука фиксируется как degraded-событие и попадает в receipt. Утверждение «тесты прошли» без receipt на текущий fingerprint ловит stop-гейт: в `strict` блокирует, в `soft` предупреждает. Режим `strict` включён по умолчанию для маршрутов `high`.
5. **Установка: обязательное сразу, остальное по необходимости.** Флагов «поставить или нет» у пользователя нет.
   - **Обязательный базис, без вариантов и без способа пропустить.** Ставится сразу при установке:
     - базы безопасности: OSV CVE и закреплённый OpenGrep с правилами Getzilla;
     - Superpowers, BMAD и Spec Kit — закреплённых версий из `toolchain.json`, проверенных по тегу и commit, и подключённых к выбранному агенту штатным механизмом каждого upstream.

     Если что-то из базиса не встало, установка **не завершена**: ненулевой код выхода, состояние `incomplete`, `doctor` красный, `verify --mode pr` провален. Повторный запуск дотягивает недостающее.
   - **По необходимости — автоматически.** Всё остальное Getzilla подтягивает сам в момент, когда это понадобилось, без вопросов:
     - файлы для ещё одного агента — как только он обнаружен или выбран;
     - `factory/` — при первом обращении к фабрике;
     - доменные пакеты (Bitrix, PHP) — когда профиль репозитория их требует.

     Каждое такое добавление записано в managed-манифест и видно в `git status` и change record.
   - **Одна копия вместо пяти.** Скиллы и описания агентов хранятся в одном каноническом месте. Для каждого используемого агента ставятся только его тонкие обёртки.

   План установки показывает число файлов и байт по компонентам.
6. **Реестр обещаний.** Каждая фраза лендинга, обещающая поведение, ссылается в `claims.json` на механизм, тест и условие («требует Trust CI», «требует branch protection»). Тест падает, если у обещания нет такой ссылки. Лендинг показывает условие рядом с обещанием.
7. **Стековые проверки с тулчейнами по необходимости (Windows в первую очередь).** Реестр стеков `stacks.json`. Для каждого стека описаны:
   - признаки в репозитории;
   - закреплённый тулчейн с официальным источником и контрольной суммой для Windows, Linux и macOS;
   - проверки: сборка, тесты, линтер, форматтер, уязвимости через OSV офлайн.

   Обнаружен стек — тулчейн скачивается сам, в пользовательский каталог `~/.getzilla/toolchains/` без прав администратора и без правки системного PATH, и проверки запускаются. Не скачался или требует администратора (MSVC Build Tools для Rust на Windows) — это `fail` с причиной и инструкцией, а не `skip`. Стек без проверок в реестре помечается `STACK_NOT_VERIFIED`, и это видно в receipt.
8. **Измерение выгоды.** Счётчики по маршрутам: время, число ревью, прогоны verify, блокирующие находки до merge. Отчёт `getzilla report`.

## 1.6. Вне scope

- Рантайм-перехват расходов агента или n8n в момент выполнения (прокси, биллинг).
- Изменение настроек GitHub без явного «да» владельца: `getzilla ci protect` только печатает план (`--plan`), применение отдельным подтверждением.
- Классификация риска языковой моделью. Нужна детерминированная и тестируемая.
