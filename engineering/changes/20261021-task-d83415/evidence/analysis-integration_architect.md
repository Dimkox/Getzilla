## Existing integration points

- `.getzilla/getzilla/verification.py:1323`: `_secret_scan` uses `pattern.search` and emits one error per pattern/file. It must enumerate occurrences before any precise disposition can be safe.
- `verification.py:1251`: `_git_diff_check` checks the worktree, index and every selected committed range. It retains command output but currently gives one error per failed command. Disposition matching must respect the snapshot each command examined.
- `verification.py:2640`: both checks run through `_CheckDispatch`; a failed check can prevent later checks from running. Apply dispositions within the check before dispatch, never by rewriting the completed report.
- `quality_gates.py`: these checks are mandatory. Preserve executed pass/fail statuses; a disposition is not a skip. Overall verification derives failure from check status, not directly from detail severity.
- `util.py:407`: the fingerprint binds HEAD and changed-path bytes. Untracked `.getzilla/runtime` content is excluded. Existing `load_json` silently defaults on malformed/unreadable files and is unsuitable for authoritative disposition loading.
- `scripts/getzilla_verify.py`: JSON preserves arbitrary detail fields; text renders severity, path and message. Put the disposition ID and original observation in the displayed message as well as structured fields. `scripts/getzilla_report.py` is a metrics report, not the verification report formatter.

## Minimal compatible design

1. Add one small shared disposition loader/matcher, called by both checks. Use a fixed repository-relative, versioned JSON path with strict validation. Absence means no dispositions. A present invalid, unreadable, oversized, symlinked or nonregular file produces a blocking configuration finding. Reject duplicate JSON keys, unknown fields, unsupported versions/kinds, duplicate IDs, noncanonical/traversing paths, invalid hashes and unsupported finding codes. Do not use `load_json` or partial acceptance of valid entries from an invalid document.
2. Prefer target-owned `engineering/verification-dispositions.json`, outside installer-managed directories. If the chosen path is under `.getzilla`, explicitly protect consumer policy from install/update replacement; `.getzilla` is wholly managed by `scripts/install_into.py`. Never keep authoritative policy in runtime. Record the configuration path and SHA-256 in report metadata and ensure its bytes participate in source stability and receipt binding, including ignored/untracked cases. A tracked file uses the existing fingerprint naturally; any out-of-tree or ignored authority needs an explicit digest binding and final recheck.
3. Match each generic-secret occurrence with `finditer`, without logging its captured literal. Bind exact normalized path, entire file SHA-256, finding code, occurrence location/span or occurrence digest, reviewed disposition ID, reason and evidence reference. Require the captured literal to be exactly an Ethereum address (`0x` plus 40 hex characters), and allow only the reviewed public token-address category. Address shape alone is not public-token proof. The exact reviewed entry supplies that context. Continue scanning the entire file and every other pattern. Private-key and AWS matches remain errors; an approved address beside another secret cannot clear the second occurrence.
4. Keep the original code/path/message and original severity visible. Set only the matched occurrence's effective severity to `info`, with disposition ID, reason, configuration digest and observed file digest. Count observed, dispositioned and unresolved findings separately. The check passes only when unresolved errors are zero and policy validation succeeded. Raw observations remain present in JSON and text. Retain schema version 1 with additive fields where compatible; do not require consumers to infer disposition from a missing finding.
5. For whitespace, restrict the supported disposition category to reviewed immutable Markdown and named whitespace diagnostics. Parse every diagnostic from every command. Match a file hash to the exact source snapshot: worktree bytes, index blob for cached checks, HEAD blob for committed ranges. Require exact path/hash and diagnostic identity; an unrelated current-file hash cannot clear an index or range finding. Preserve stdout, stderr and raw exit status. Unknown output, non-whitespace Git errors, mixed covered/uncovered diagnostics or parse ambiguity must fail. Hash changes remove coverage; paths and changed-file status never grant exemptions.
6. No quality-gate skip allowlist change is needed. Invalid policy must also fail when there are no matching findings. Resolve the loader once per run or ensure all uses bind the same digest. Source stability must reject a policy change during scanning.

## Packaging and verification consequences

The manifest recursively includes regular source files except its declared exclusions. A new `.getzilla/getzilla` Python module is automatically packaged and installed. A separate JSON schema outside managed directories must be added to `MANAGED_FILES` if installed consumers need it. Runtime files never ship. Regenerate the manifest through existing tooling after source changes; preserve historical release archives. Avoid shipping consumer-specific reviewed entries as Getzilla defaults.

Focused regression coverage should prove: multiple matches on one line/file; approved address plus unapproved secret/private key; malformed configuration with zero observed findings; changed bytes and occurrence drift; path traversal/symlink refusal; staged versus HEAD/worktree hash mismatch; mixed/unknown Git diagnostics; retained raw findings with effective info; fingerprint change after policy edits; and installed/package availability. Existing tests in `tests/test_verification_doctor.py` cover committed and staged whitespace; `tests/test_util_fingerprint.py` and `tests/test_manifest_package.py` cover the other boundaries. The full external Liqvera audit must then execute with zero gaps. A passing disposition unit test does not establish that acceptance.
